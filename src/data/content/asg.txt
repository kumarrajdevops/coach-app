[STAGE knowledge]
HEADING: The 2am problem a single EC2 instance can't solve
[P]
Your EC2 instance from the last lesson works — right up until the night real traffic triples during a launch and it falls over, or someone fat-fingers a termination in the console and the whole site goes down until a human notices and relaunches it by hand. A single hand-launched instance has no way to react to either problem on its own — it can't add capacity under load, and nothing is watching to replace it if it dies. That's the actual gap an Auto Scaling Group (ASG) closes: a declared range of how many instances should exist, kept true automatically, with no one paged at 2am to do it by hand.

[STAGE pieces]
HEADING: Launch templates, min/desired/max, scaling policies, health checks
[DIAGRAM nodes="Client|Load Balancer|Target Group|ASG|EC2 instance" highlight="ASG"]
[DEFS]
Launch template :: the actual instance definition an ASG uses whenever it needs to create a new instance — AMI, instance type, key pair, Security Group, user-data, all of it, identical to what you launched by hand in the EC2 lesson. Launch configurations are the older, now-legacy version; AWS no longer lets you create new ones — always use a launch template.
Min / Desired / Max capacity :: the three numbers that define an ASG's range. **Min** is the floor — it will never scale below this even with zero traffic. **Max** is the ceiling — a safety cap so a scaling bug can't launch hundreds of instances and run up a huge bill overnight. **Desired** is the current target the ASG is actively trying to maintain right now, and moves between min and max as scaling policies fire.
Scaling policy :: the rule that decides when desired capacity changes. **Target tracking** is the default to reach for — "keep average CPU at 60%" — and AWS works out the add/remove math itself, like a thermostat. **Step scaling** is manual: you define exact thresholds and exact instance-count changes yourself. **Scheduled scaling** changes desired capacity at specific times (e.g. scale up before a known Monday-morning spike) and doesn't react to metrics at all.
Health check type: EC2 vs ELB :: by default an ASG only asks "is this instance's EC2 status check passing" — is the VM itself alive. It has **no idea** whether the app inside is actually working. Setting the health check type to **ELB** instead makes the ASG ask the load balancer's own target-group health check — an actual HTTP request to your app — which is the one that catches "the instance is up but nginx crashed." We'll hit exactly this gap in the troubleshoot step below.
[TABLE]
 | Launch template | Launch configuration
Introduced | 2017, the current standard | The original (2013) mechanism — legacy now
Mutability | Versioned — create v1, v2, $Latest, roll back anytime, the ASG just tracks a version | Immutable — to change anything you must create an entirely new one and repoint the ASG at it
Mixed instances / Spot+On-Demand | Supports a mixed instances policy — one ASG spanning several instance types and blending Spot with On-Demand for cost savings | Cannot do this at all — one instance type, one purchase option, full stop
New feature support | Gets every new EC2 launch feature as AWS ships it (placement groups, multiple ENIs, newer burst/credit options, etc.) | Frozen — missing most capabilities added since 2017
Can you still create new ones? | Yes, always | No — AWS blocks creating new launch configurations in current accounts; only pre-existing ones keep working
[NOTE]
Why this is worth knowing precisely, not just "templates are newer": the mixed-instances/Spot capability is the real dealbreaker, not versioning convenience. An ASG that wants to blend cheaper Spot capacity with a baseline of On-Demand instances — a very common real cost-optimization pattern — is only possible on a launch template. A launch configuration structurally cannot express it. If you ever inherit an ASG still running on a launch configuration, migrating it to a launch template isn't just tidiness — it's unlocking capabilities that were never available before.

[STAGE hands-on]
HEADING: Launching a healthy, self-maintaining ASG via CLI
[P]
Same Security Group and key pair from the EC2 lesson — this builds directly on that, not a fresh setup.
[CODE lang=bash caption="1. create a launch template — the same instance definition as the manual EC2 launch"]
aws ec2 create-launch-template \
  --launch-template-name web-template \            # name referenced by the ASG below
  --version-description "nginx web server" \        # human-readable note on this version
  --launch-template-data '{
    "ImageId": "ami-0abcd1234efgh5678",              # same AMI as the manual EC2 lesson
    "InstanceType": "t3.micro",
    "SecurityGroupIds": ["sg-0123456789abcdef0"],    # the web-sg from the EC2 lesson
    "KeyName": "your-keypair-name",
    "UserData": "<base64-encoded nginx install script from the EC2 lesson>"
  }'
[CODE lang=bash caption="2. create the ASG itself — min=2, desired=2, max=4"]
aws autoscaling create-auto-scaling-group \
  --auto-scaling-group-name web-asg \               # the ASG's name
  --launch-template "LaunchTemplateName=web-template,Version=\$Latest" \ # always track the latest template version
  --min-size 2 --desired-capacity 2 --max-size 4 \  # the min/desired/max trio from the pieces step
  --vpc-zone-identifier "subnet-aaa,subnet-bbb"     # spread across 2 subnets/AZs — one AZ dying shouldn't take the whole fleet down
[CODE lang=bash caption="3. confirm it's healthy — 2 instances, both InService"]
aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names web-asg \
  --query 'AutoScalingGroups[0].Instances[].[InstanceId,LifecycleState,HealthStatus]' --output table
# Expect two rows, both "InService" / "Healthy" — the ASG launched exactly `desired-capacity`
# instances on its own, no manual run-instances call needed

[STAGE key-insight]
HEADING: Why the ASG didn't notice
[NOTE]
This is a direct, real consequence of the health-check-type setting from the pieces step, not a hypothetical. With the default EC2 health check, the ASG is only ever asking AWS's own hypervisor "is this VM still running" — it never makes an HTTP request, so it genuinely cannot see that nginx crashed. The instance can sit there broken, counted as healthy, taking its share of traffic and returning nothing, until a human notices. Setting the health check type to ELB (which needs a target group — the ALB & NLB page builds that next) is what actually closes this gap, because then the ASG's definition of "healthy" becomes "the load balancer's own HTTP health check against this instance is passing," not just "the VM booted."

Two things to tighten: (1) you said ASG will "restart" the instance — it doesn't restart anything in place, it terminates the unhealthy instance and launches a brand-new one from the launch template to replace it. CLARIFICATION: **The actual fix, concretely:** (1) create a target group with an HTTP health check (e.g. path `/`, a healthy/unhealthy threshold, a check interval) and register the ASG's instances with it. (2) Explicitly set the ASG's health check type to ELB — being behind a target group alone doesn't change what the ASG listens to: `aws autoscaling update-auto-scaling-group --auto-scaling-group-name web-asg --health-check-type ELB --health-check-grace-period 300`. The grace period matters too — it tells the ASG to ignore health check failures for the first N seconds after a new instance launches, so a slow-booting app doesn't get flagged unhealthy before it's even finished starting.

**On "restart" vs "replace":** this isn't just a word choice — an ASG's self-healing is terminate-and-replace-from-template, never an in-place restart. That's exactly why a failure baked into the launch template (a broken user-data script, for instance) defeats ASG self-healing entirely — every replacement instance boots from the same broken template and fails identically. ASG protects you from *transient* failures (a process crashing, a host dying) — it cannot protect you from a *systemic* one baked into what it's deploying. That's a real interview distinction: "does ASG make your deployment reliable" — no, it makes a reliable deployment *resilient*; it doesn't fix a broken one.

You were right that target groups/ELB are the mechanism — just make the actual two-step config explicit next time a question asks for "the fix," not just the general direction.

Fault 1: instance terminated directly, replacement appeared in ~1 minute, desired capacity restored with no human involved — the actual self-healing promise, verified for real. Fault 2: nginx killed under the default EC2 health check, ASG kept reporting Healthy/InService — nothing happened, confirming Round 1's diagnosis wasn't just theory. CLARIFICATION: **Why fault 1 and fault 2 behave so differently, mechanically:** fault 1 (direct termination) is a *state change AWS itself tracks* — EC2 knows immediately that the instance is gone, and the ASG reconciles "desired=2, actual=1" against that authoritative state on its own polling cycle, which is where your ~1 minute came from. It's not a health-check delay — it's "the instance now provably doesn't exist." Fault 2 is completely different: the instance still *exists* and still *passes* the only check being asked (EC2 status check, "is the VM alive") — so there's no delay to wait out, because there's no failing signal at all. The ASG isn't slow to notice fault 2 — it is permanently blind to it until the health check type changes.

**Your doubts, answered:**

1. **Transient vs. systemic failures:** *Transient* = something that goes wrong with one instance, independent of the others — a process crashing, a host having a bad day, a brief resource spike. Replacing that one instance genuinely fixes it. *Systemic* = a bug baked into what every instance is built from — a broken user-data script, a bad AMI, a config error in the launch template. Every replacement instance inherits the exact same bug and fails the exact same way; ASG will cheerfully replace it forever without ever fixing anything, which is exactly the trap from Round 1's clarification.

2. **How to stop/remove an instance from an ASG on purpose** (without it immediately being replaced): don't just `terminate-instances` directly unless you want the replacement — that's what triggered fault 1. To remove one instance without a replacement, lower desired capacity first, or use `aws autoscaling terminate-instance-in-auto-scaling-group --instance-id <id> --should-decrement-desired-capacity` (removes it *and* adjusts desired capacity down by one, so the ASG doesn't launch a replacement). To pull an instance out temporarily for inspection — without terminating it or touching desired capacity — use `aws autoscaling enter-standby --instance-ids <id> --auto-scaling-group-name web-asg --should-decrement-desired-capacity`; the ASG stops counting it and launches a replacement to cover it, but your original instance stays alive and untouched for you to debug.

3. **Debugging a systemic replace-loop** (every new instance dies the same way): the hard part is the instance disappears before you can look at it. Use `enter-standby` (above) the moment you see a new instance come up, before the ASG decides it's unhealthy and recycles it — that freezes it for inspection. Then check `/var/log/cloud-init-output.log` (the user-data script's actual output/errors) and `systemctl status <your service>`. Also check `aws autoscaling describe-scaling-activities --auto-scaling-group-name web-asg` — the `StatusMessage` field on recent activities often states directly why an instance was terminated/replaced.

4. **LifecycleState** is the ASG's own answer to "what stage of its life is this instance in" — `Pending` (launching, not yet serving traffic or counted as InService) → `InService` (actively running and counted toward desired capacity) → `Terminating` → `Terminated`. This is a different axis from **HealthStatus** (`Healthy`/`Unhealthy`) — LifecycleState is *where in its lifecycle* the instance is; HealthStatus is *whether the ASG currently considers it good*. An instance can be `InService` and still `Unhealthy` for a moment before the ASG acts on it — they're tracked and reported separately, which is exactly why your `describe-auto-scaling-groups` queries pulled both columns.


[STAGE fault-injection]
HEADING: A real systemic replace-loop
[P]
A teammate pushes a "quick fix" to the launch template — renames the key pair, or points at a Security Group that got deleted last week — and ships it without testing. Every single new instance the ASG tries to launch now fails for the exact same reason. This is the systemic failure from Round 1's clarification, made real: worth seeing what it actually looks like in `describe-scaling-activities` before you hit it for real at 2am.
[CODE lang=bash caption="1. break the launch template on purpose — point it at a key pair that doesn't exist"]
aws ec2 create-launch-template-version \
  --launch-template-name web-template \
  --source-version 1 \                         # base the new version on version 1
  --launch-template-data '{"KeyName": "definitely-does-not-exist"}' \ # the broken field
  --version-description "BROKEN on purpose - bad key name"
# This becomes the new $Latest version — the ASG's launch template config
# already tracks $Latest, so it'll be used for the next launch attempt
[CODE lang=bash caption="2. force the ASG to launch against the broken version"]
aws autoscaling start-instance-refresh --auto-scaling-group-name web-asg
# This cycles every instance through the current $Latest template version —
# i.e. the broken one
[CODE lang=bash caption="3. watch it fail, repeatedly, for the same reason every time"]
aws autoscaling describe-scaling-activities --auto-scaling-group-name web-asg \
  --query 'Activities[0:5].[StatusCode,StatusMessage]' --output table
# Expect StatusCode "Failed" on repeated activities, and StatusMessage naming
# the exact problem: the key pair doesn't exist. No instance ever reaches
# InService - desired capacity never gets restored while this is broken
[CODE lang=bash caption="4. fix it — point back at a real key pair, confirm recovery"]
aws ec2 create-launch-template-version \
  --launch-template-name web-template \
  --source-version 1 \
  --launch-template-data '{"KeyName": "your-keypair-name"}' \ # the real key pair again
  --version-description "fixed - restored real key name"
aws autoscaling start-instance-refresh --auto-scaling-group-name web-asg
# Then re-check describe-auto-scaling-groups — both instances should reach
# InService / Healthy again
[NOTE]
Notice what's different from the nginx fault earlier: that one never showed up anywhere in the ASG's own tooling, because the instance successfully existed and passed the only check being asked. This one shows up immediately and explicitly in describe-scaling-activities, because the failure happens at launch time, before an instance even exists to be falsely marked healthy. Same underlying lesson as the whole page: the ASG can only ever react to what it's actually told to check — a launch-time failure it always sees; an in-instance app failure it's blind to until the health check type changes.

**Your new doubt, for future reference — instance type not supported in an AZ:** your own diagnosis and fix are exactly right. A regional instance type like `t3.micro` isn't guaranteed to be offered in every Availability Zone, and this is easy to get tripped up by because of a genuinely confusing AWS quirk: **AZ names like `us-east-1e` don't map to the same physical datacenter across different AWS accounts.** AWS deliberately shuffles the name-to-physical-location mapping per account to spread load evenly across the region. So "us-east-1e" showing as `Available` just means that slot is up — it says nothing about which instance types that particular physical AZ (for your account specifically) happens to support. `describe-instance-type-offerings` with `--location-type availability-zone` is exactly the right tool — it tells you the truth for your own account's AZ mapping, not a generic answer you could find in docs.

**The actual fix, two options:** (1) narrow `--vpc-zone-identifier` on the ASG to only the subnets/AZs that actually offer the instance type (drop the problematic one), or (2) pick an instance type with broader availability if you don't have a hard requirement for `t3.micro` specifically. Option 1 is usually better — you want the ASG constrained to AZs you've *confirmed* work, not hoping every AZ behaves the same.


[STAGE conclusion]
HEADING: What ASG alone still can't do
[P]
You can now launch a self-healing fleet instead of a single instance, read its own activity history to diagnose exactly why a launch failed, and you've proven two very different failure classes with your own hands: a transient one (direct termination) that self-heals cleanly, and a systemic one (a broken launch template) that the ASG's own tooling surfaces clearly through `describe-scaling-activities` and `describe-instance-refreshes`.
[P]
What's still unsolved is the gap from Round 1: an in-instance app crash that leaves the VM itself perfectly healthy. The ASG can't close that on its own — it needs something that actually asks the app "are you working," not just "are you alive." That's exactly what a load balancer's target group provides, and it's what the next page builds: wiring an ALB in front of this ASG, switching the health check type to ELB, and finally closing the one gap that's followed this whole module from the start.
