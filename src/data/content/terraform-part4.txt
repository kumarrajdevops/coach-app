[STAGE knowledge]
HEADING: tf3a and tf3b were identical in shape, arbitrary in purpose
[P]
Part 3 closed the "same stack, written twice" gap with modules - but tf3a and tf3b have no real identity. Nothing marks either one as "the one that matters" versus "the one it's fine to break." Real infrastructure needs exactly this distinction: a dev environment where mistakes are cheap and a prod environment where they're not, built from the same module, but with real safeguards against ever applying the wrong input to the wrong one. "I meant to apply to dev but it hit prod" is a well-documented, real class of incident - not a hypothetical scaremongering example - and it happens specifically because Terraform, left to defaults, makes dev and prod look nearly identical from the command line.

[STAGE pieces]
HEADING: workspaces, separate state files, separate directories - three different isolation strategies
[DIAGRAM nodes="modules/web-stack/ (one module)|dev workspace / dev.tfvars|prod workspace / prod.tfvars|terraform plan -var-file|same code, different state" highlight="dev workspace / dev.tfvars|prod workspace / prod.tfvars"]
[DEFS]
terraform workspace :: a named, isolated state namespace within ONE working directory - the same .tf files, but `terraform workspace select prod` points every subsequent plan/apply at a completely separate state file behind the scenes. `terraform.tfstate.d/<workspace>/terraform.tfstate` is where each one actually lives on local state.
terraform.workspace :: a built-in reference available inside any .tf file, resolving to the currently selected workspace's name as a plain string - usable in resource names, tags, or to pick values out of a map, without needing a separate variable for it.
-var-file :: an explicit flag supplying a whole file of variable values at once - `terraform plan -var-file=dev.tfvars` - the deliberate alternative to the auto-loaded terraform.tfvars from Part 2, used specifically when there's more than one environment and no single file should auto-load by default.
Separate state file (per environment, same workspace) :: using `-state=dev.tfstate` / `-state=prod.tfstate`, or a different backend configuration per environment, instead of workspaces - a second, independent way to keep environments from ever sharing one state file.
Separate directories (per environment) :: the most explicit isolation of all - envs/dev/ and envs/prod/ as entirely separate working directories, each with its own small main.tf that calls the same shared module with different variable values, each with its own independent state by construction, not by a flag you have to remember.

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }

provider "aws" {
  region = "us-east-1"
}

locals {
  # terraform.workspace resolves to whatever `terraform workspace select` last set -
  # this map is how ONE config produces different real values per environment
  env_config = {
    dev = {
      instance_type = "t3.micro"
      asg_min_size  = 1
      asg_max_size  = 2
    }
    prod = {
      instance_type = "t3.small"
      asg_min_size  = 2
      asg_max_size  = 6
    }
  }
}

module "web" {
  source           = "../modules/web-stack"
  project_name     = "tf4-${terraform.workspace}"      # "tf4-dev" or "tf4-prod", automatically
  ami_id           = "ami-0abcd1234efgh5678"
  instance_type    = local.env_config[terraform.workspace].instance_type
  key_name         = "your-keypair-name"
  allowed_ssh_cidr = "203.0.113.5/32"
  vpc_cidr         = terraform.workspace == "prod" ? "10.9.0.0/16" : "10.8.0.0/16"
  asg_min_size     = local.env_config[terraform.workspace].asg_min_size
  asg_max_size     = local.env_config[terraform.workspace].asg_max_size
  public_subnets = {
    a = { cidr_block = terraform.workspace == "prod" ? "10.9.1.0/24" : "10.8.1.0/24", availability_zone = "us-east-1a" }
    b = { cidr_block = terraform.workspace == "prod" ? "10.9.2.0/24" : "10.8.2.0/24", availability_zone = "us-east-1b" }
  }
}

output "alb_dns_name" {
  value = module.web.alb_dns_name
}

[STAGE troubleshoot]
HEADING: The exact "applied to the wrong environment" scenario, reproduced
[P]
Approach 2's two commands LOOK almost identical - the only difference between hitting dev and hitting prod is which two flag values got typed. Here's the realistic version of the mistake: switching between a few terminal tabs, you mean to re-apply dev after a small instance_type change, but paste a command still holding yesterday's prod state flag from your shell history.
[CODE lang=bash caption="the typo that looks almost identical to the safe version"]
# intended:
terraform apply -state=dev.tfstate  -var-file=dev.tfvars

# what actually got run - one flag behind, pulled from shell history
terraform apply -state=prod.tfstate -var-file=dev.tfvars
[P]
Terraform does not warn you here. -state=prod.tfstate is a completely valid, existing state file; -var-file=dev.tfvars is a completely valid, existing variables file. Nothing about this command is malformed - it successfully applies dev's cheaper instance_type and lower asg_min_size directly onto prod's real, live state, silently downsizing production capacity.
[NOTE]
This is the precise, real failure mode that gives "I meant to apply to dev but it hit prod" its reputation - not a hypothetical, a documented and common incident shape at real companies, because two independently-correct-looking flags can combine into a completely wrong, completely silent result. Workspaces reduce this risk by making the CURRENT target a single, visible, stateful selection (terraform workspace show) instead of two flags that have to be remembered together and kept in sync by hand, every single command. Separate directories remove it almost entirely - the directory you are physically in IS the environment, with no flag combination able to override that.

[STAGE key-insight]
HEADING: Isolation strength is not the same question as workflow convenience
[NOTE]
Workspaces are the lightest-weight option - one directory, one terraform init, fast to switch between with a single command - but that lightness is exactly the risk surface in the troubleshoot above: the "current" workspace is global, easy to forget you're in, and nothing stops a typo'd apply from landing in whichever one happens to be selected at that moment. Separate state files via explicit flags make isolation deliberate and visible in the command itself, but require remembering to pass BOTH flags together, correctly, every time - one flag updated and the other forgotten is exactly how the troubleshoot scenario happens. Separate directories are the most foolproof - the working directory itself is the safeguard, no flag or selected-state to get out of sync - at the real cost of more files to keep in sync when the shared module's calling pattern needs to change (every environment's main.tf needs the same edit, separately, unless something like Terragrunt is layered on top to generate them). None of these is strictly "the correct" choice - production teams use all three, chosen for how severe a wrong-environment mistake would actually be. The higher the real cost of hitting prod by accident, the more this page's hierarchy favors directories over state-file flags over workspaces.

CLARIFICATION: Full answer for the record. Part 1 - the precise mechanism: -state and -var-file are two SEPARATE, INDEPENDENT flags you must keep in sync by hand on every single command - nothing stops you from pairing state=prod with vars=dev, because Terraform has no concept that these two flags are "supposed to" travel together. A workspace collapses that into ONE selection: terraform workspace select prod sets a single, stateful "current target," and every subsequent plan/apply - with no flags needed at all - reads from that one selection consistently. There is no second, independent value that could possibly drift out of sync with it, because there is nothing else to select. The real remaining risk, which you also correctly named, is forgetting which workspace is currently selected - a different, weaker risk (one fact to forget) than two flags silently drifting apart (two facts to keep paired correctly, forever). Part 2 - a wrong flag requires getting something WRONG while everything else looks right - the command runs in the correct directory, the correct main.tf, you just typed or pasted one incorrect value among several correct-looking ones; nothing about the moment of typing it looks unusual. A wrong directory requires being somewhere else entirely - and that fact is visible BEFORE you ever run a command, in your own shell prompt (exactly like the real MINGW64 prompt in your own terminal output, which literally names the current directory every single time). This is the actual distinction asked for: a wrong flag is only ever caught AFTER running the command, usually after seeing the plan's diff (if you read it carefully) or worse, after apply. A wrong directory is catchable BEFORE running anything, just by glancing at the prompt - the mistake is visible at the point you'd make it, not just at the point you discover its consequences. Part 3 - the concrete material that justifies recommending directories specifically: this page's own troubleshoot section demonstrated terraform apply -state=prod.tfstate -var-file=dev.tfvars succeeding completely silently, with Terraform having zero way to detect the combination was wrong - and the real incident in doubt 2 below is the workspace equivalent of that exact failure mode, now lived through for real. When a mistake can be both completely silent AND cause real financial damage, the right default is whichever approach makes the mistake impossible to make quietly - which is directories, specifically because the safeguard (being in the right place) is checked by the human before the command runs, not inferred by Terraform after.

What happens across Terraform version changes (upgrades)? :: Two separate things change independently: the Terraform CLI/core version (what you install via winget, currently 1.17.x) follows its own release notes for new language features, deprecations (like -state's deprecation warning you hit), and bug fixes - your required_version constraint in the terraform {} block controls which CLI versions are even allowed to run your config. The PROVIDER version (hashicorp/aws, currently pinned to ~> 5.0 after today's fix) is entirely separate - it tracks AWS's own API surface and gets its own changelog, its own breaking changes between major versions, and its own lock file entry. Upgrading either one deliberately (terraform init -upgrade for providers; reinstalling Terraform itself for core) is safe practice; having NO version constraint at all - what approach-2 actually had until today - means an ordinary init can silently jump to a newer major version of either one without you ever deciding to.
Is the right hierarchy "use separate directories, otherwise workspaces, but never separate tfvars (approach 2)"? :: Close, but "never" approach 2 is stronger than this page's own material actually supports - the real ordering, grounded in everything covered: directories are safest by construction (no flag or selection to forget), workspaces are next (one single selection, but still something to forget), and separate state-file flags are the weakest precisely because two independent things must be kept in sync by hand every time - and today you also learned that approach was actually using a deprecated -state flag, which argues even harder against it. Why is -state deprecated, and what should approach 2 use instead? :: Confirmed directly from terraform plan -help: -state=statefile is explicitly labeled "A legacy option used for the local backend only." The honest trade-off, worth knowing before switching: this is MORE friction than the deprecated flag, not less - switching environments now requires a full re-init, not just different flags - which is itself a real point in favor of approach 3 over approach 2 generally.
What actually happens in approach 2 if neither -state nor -var-file is given? :: Two different outcomes. Missing -var-file: every variable in variables.tf is required with no default, so Terraform interactively prompts you at the terminal for each one, one at a time (var.project_name, Enter a value: ...) - blocking until answered, or erroring immediately only in a non-interactive context like CI. Missing -state is the more dangerous half: Terraform silently falls back to a generic terraform.tfstate file in the current directory - neither dev's nor prod's - potentially creating a THIRD, completely untracked set of resources with no connection to either environment's real state. Confirmed your own directory doesn't have one of these stray files yet, since you've always passed -state explicitly so far - but the risk is real the moment that flag is ever forgotten.

This page set out to answer "how do you keep dev and prod apart," and ended up teaching something sharper: the difference between a mistake Terraform can catch and a mistake only a human can prevent. [BULLETS]
Workspaces, separate state-file flags, and separate directories all genuinely work - the real difference between them isn't correctness, it's how much of the safety depends on a human remembering something correctly, every single time, forever.
Approach 2's two independent flags and approach 1's single forgotten workspace selection are the same underlying risk wearing two different shapes - something that must be kept correct by memory alone, with nothing in the tool itself checking it.
Approach 3 isn't safer because directories are magic - it's safer because the safeguard (being in the right place) is visible to a human BEFORE a command runs, not something Terraform infers after.
lifecycle { prevent_destroy = true } is the one guardrail from today that isn't a habit at all - it's enforced by Terraform itself, the same category of protection as a ForceNew check or a required variable, not the same category as "remember to check."
