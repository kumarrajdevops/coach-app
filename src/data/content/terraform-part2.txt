TITLE: Terraform — Part 2: Variables & count/for_each
COVERED: 2026-10-29

[STAGE knowledge]
HEADING: The same stack, with every hardcoded value given exactly one home
[P]
Part 1 built a real EC2 → ASG → ALB → VPC stack with every value typed directly into the resource blocks — and that honesty is exactly what made two real problems visible instead of theoretical: the AMI id sitting in two separate places, and a copy-pasted subnet whose availability zone was silently left pointing at the wrong one. Both were "you'd only notice if you went looking for it" bugs. Part 2 fixes the actual structural cause, not just those two spots — every value that could ever be typed more than once gets pulled out into a `variable`, declared exactly once, referenced everywhere it's needed. The subnet/route-table-association pattern you had to repeat by hand in Part 1 (and again building your own "tuf1" VPC) also gets rebuilt here using `count`, so adding a third subnet is a one-line change instead of three new resource blocks.

[STAGE pieces]
HEADING: variable, var.name, terraform.tfvars, locals, count, for_each
[DIAGRAM nodes="variables.tf (declares)|terraform.tfvars (supplies values)|main.tf (var.x references)|terraform plan|terraform apply" highlight="variables.tf (declares)|terraform.tfvars (supplies values)"]
[DEFS]
variable block :: declares an input - a name, a type, optionally a description and a default. `variable "instance_type" { type = string, default = "t3.micro" }` - this is a declaration, not a value assignment by itself.
var.name :: how a resource block reads a declared variable's actual value - `instance_type = var.instance_type`. Exactly one place in the whole config ever defines what that value actually is.
terraform.tfvars :: a file Terraform auto-loads with no flag needed, purely because of its exact filename, to supply/override variable values - `instance_type = "t3.micro"` here overrides that variable's own default. A differently-named file needs `-var-file=something.tfvars` explicitly.
locals block :: a named expression computed once and reused, NOT an input like a variable - `locals { common_tags = { Project = var.project_name } }`. Use a variable for something someone else should be able to override from outside; use a local for something derived purely from values already inside the config.
count :: a meta-argument that creates N copies of a resource, addressed by position - `aws_subnet.public[0]`, `aws_subnet.public[1]`. `count.index` inside the block is that position, usable to index into a parallel list like `var.public_subnet_cidrs[count.index]`.
for_each :: the same idea, but addressed by a stable key instead of a position - over a map (`each.key`/`each.value`) or a set of strings (`each.key` == `each.value`). `aws_subnet.public["a"]`, `aws_subnet.public["b"]`.
splat expression :: `aws_subnet.public[*].id` - "every `.id` from this count-based resource," a compact way to turn a list of resource objects into a list of just one of their attributes. Needed constantly once subnets exist via `count`, since `aws_lb.subnets`/`aws_autoscaling_group.vpc_zone_identifier` both want a plain list of ids.

[STAGE troubleshoot]
HEADING: Reordering a list that didn't conceptually change anything
[P]
Nothing about the stack needs to change - still exactly 2 public subnets, same 2 CIDRs, same 2 AZs. But you decide `us-east-1b` should be listed first for readability, and swap the order in both lists at once, keeping each CIDR correctly paired with its AZ:
[CODE lang=hcl caption="the only edit made - both lists reordered together, pairing preserved"]
variable "public_subnet_cidrs" {
  default = ["10.4.2.0/24", "10.4.1.0/24"]      # was ["10.4.1.0/24", "10.4.2.0/24"]
}
variable "public_subnet_azs" {
  default = ["us-east-1b", "us-east-1a"]        # was ["us-east-1a", "us-east-1b"]
}
[CODE lang=bash caption="terraform plan - NOT a no-op"]
terraform plan
# aws_subnet.public[0] will be updated in-place... no, actually:
#   ~ availability_zone = "us-east-1a" -> "us-east-1b" # forces replacement
#   -/+ resource "aws_subnet" "public" {
# aws_subnet.public[1] shows the mirror image
# Plan: 2 to add, 0 to change, 2 to destroy
[P]
`count.index` is just position in a list - `aws_subnet.public[0]` means "whatever is at index 0 right now," not "the specific subnet I originally called public_a." Reordering the list changes what's AT position 0, and from Terraform's point of view that's indistinguishable from actually changing the first subnet's AZ - the exact same `-/+ replace` as if you'd genuinely edited it by hand. If this ASG already had running instances, that replacement destroys and recreates both subnets - taking every instance's network interface with them.

[STAGE key-insight]
HEADING: count ties identity to position; for_each ties it to a name
[NOTE]
This is the structural reason `for_each` exists, not just a style preference. A `count`-based resource's identity IS its position - there's no way to tell Terraform "this is still conceptually the same subnet, I just reordered my source list." A `for_each`-based resource's identity is its KEY, and map keys have no inherent order at all - reordering a map's entries is a complete no-op, because there's no "position" for the reorder to even apply to.
[CODE lang=hcl caption="the same two subnets, rewritten with for_each and a map keyed by name instead of position"]
variable "public_subnets" {
  description = "Keyed by a stable name, not list position - reordering this map can never trigger a replacement"
  type = map(object({
    cidr_block        = string
    availability_zone = string
  }))
  default = {
    a = { cidr_block = "10.4.1.0/24", availability_zone = "us-east-1a" }
    b = { cidr_block = "10.4.2.0/24", availability_zone = "us-east-1b" }
  }
}

resource "aws_subnet" "public" {
  for_each                = var.public_subnets
  vpc_id                  = aws_vpc.main.id
  cidr_block              = each.value.cidr_block
  availability_zone       = each.value.availability_zone
  map_public_ip_on_launch = true
  tags = { Name = "${var.project_name}-public-${each.key}" }    # aws_subnet.public["a"], aws_subnet.public["b"]
}

resource "aws_route_table_association" "public" {
  for_each       = aws_subnet.public
  subnet_id      = each.value.id
  route_table_id = aws_route_table.public.id
}
[NOTE]
The trade-off: `aws_subnet.public[*].id` (splat, works on count) has no direct equivalent on a for_each map - you need `[for s in aws_subnet.public : s.id]` or `values(aws_subnet.public)[*].id` instead, slightly more to type for the same result. `count` also wins when you genuinely just want "N identical-ish copies" and don't care about individually addressing or naming each one. `for_each` wins the moment any single item in the set might need to be added, removed, or reordered independently without disturbing its neighbors - which, in practice, is most real infrastructure.

[STAGE key-insight]
HEADING: The actual tool for migrating count to for_each: moved blocks
[P]
Everything in the troubleshoot section above assumed switching a resource from count to list-reordering (or from count to for_each entirely) always means destroy-and-recreate. It doesn't have to. aws_subnet.public[0] and aws_subnet.public["a"] are different ADDRESSES to Terraform, but if the underlying resource's actual arguments (cidr_block, availability_zone) are identical either way, the real AWS subnet never needed to be touched at all - only Terraform's own bookkeeping of "which address does this real resource live at" needed to change. A moved block tells Terraform exactly that.
[CODE lang=hcl caption="moved blocks - count indices to for_each keys, same real resources, zero AWS changes"]
moved {
  from = aws_subnet.public[0]
  to   = aws_subnet.public["a"]
}
moved {
  from = aws_subnet.public[1]
  to   = aws_subnet.public["b"]
}

moved {
  from = aws_route_table_association.public[0]
  to   = aws_route_table_association.public["a"]
}
moved {
  from = aws_route_table_association.public[1]
  to   = aws_route_table_association.public["b"]
}
[P]
Add these alongside switching the resource's count to for_each (same apply, same config), then plan. If the subnet's own arguments haven't otherwise changed, the plan shows no destroy and no create for these resources at all - just a quiet address rename, confirmed in the plan output as "resource address changed" rather than any create/destroy symbols. The ASG and ALB downstream never see a gap, because the actual subnet ids never changed - only what Terraform calls them internally did.
[NOTE]
This is the direct, concrete answer to "what was I missing": the whole multi-step migration in this page's troubleshoot and Round 1 - new temporary CIDRs, -target, -replace, re-pointing the ASG and ALB, destroying the old subnets - was all necessary ONLY because the subnets were allowed to actually get destroyed and recreated as part of the count-to-for_each switch. A moved block sidesteps that entire category of problem for a pure address change. It does NOT help when a resource's actual arguments are genuinely changing too (a real new CIDR, a real new AZ) - that's still a real replacement, and everything from Part 1's fault-injection table still applies in full. The rule going forward: before changing count to for_each (or reordering a list, or renaming a resource block), ask "is this resource's real-world content actually changing, or just its Terraform address?" If it's purely an address change, write the moved block first and the destroy/recreate drama simply doesn't happen.

[STAGE key-insight]
HEADING: Working checklist, built from every real incident across both pages
[NUMBERED]
Read the plan's action symbol, not just the resource name, before every apply - ~ is in-place and safe by itself; -/+ is a replace, and means stop and ask "is the old one still attached to anything live?" before applying.
Predict ForceNew before you change a ForceNew-looking attribute, since it can't be read directly from your own code - a resource's vpc_id, a subnet's availability_zone, and a resource's own address (count to for_each) are the recurring culprits. When unsure, run plan only, read the symbol, decide the next move from that.
Make one structural or identity-changing edit per apply, not several stacked together - reordering a list, switching count to for_each, and using -replace on downstream resources all at once is exactly what turns a manageable change into a loop.
Reach for a moved block first when a resource's real-world content isn't actually changing, only its address - renaming, reorganizing into for_each, restructuring modules - before accepting a destroy and recreate as inevitable.
When a real replacement is unavoidable and something else depends on the old resource, sequence it yourself - -target the dependent resource first, confirm it detached, then let the old one destroy. Don't trust one big apply to order it correctly on its own.
Verify empirically, not just via terraform plan - plan only reflects what Terraform's graph can see. Check AWS directly with describe-network-interfaces, describe-auto-scaling-groups, or describe-target-health when something is genuinely ambiguous.
Let slow operations finish - an ALB taking 2 to 4 minutes to create is normal, not a hang. Interrupting mid-create is one of the most common real causes of a tainted resource.
Run a plain terraform plan again after every apply before moving on - "No changes. Your infrastructure matches the configuration." is the actual signal you're safe to continue, not just apply exiting without an error.

CLARIFICATION: Full answer for the record, tying together what actually happened. Part 2 - what really happens: count reordering plans aws_subnet.public[0] and [1] as -/+ replace, same as the troubleshoot section showed. But these subnets already have a live ASG and ALB attached (via vpc_zone_identifier and subnets, both referencing these exact subnet ids) - so when Terraform tries the destroy half of that replace, AWS rejects it with a DependencyViolation: a subnet can't be deleted while it still has active ENIs in it (the ASG instances' network interfaces, the ALB's own ENIs) - this is the EXACT SAME failure class as Part 1's security-group/ALB incidents, just one layer up the stack (a subnet instead of a security group). create_before_destroy didn't help here for a structural reason: it only reorders DESTROY-then-CREATE into CREATE-then-DESTROY for a single resource being replaced - it doesn't detach the ASG/ALB from the old subnet first, so the old subnet is still just as "in use" when its destroy is attempted, create_before_destroy or not. The actual fix is the same two-step pattern from Part 1's fault-injection table: get the ASG/ALB pointed at new subnets FIRST (a separate, deliberate step), confirm they've actually moved, THEN destroy the old subnets once nothing's attached - never let one single apply try to do both at once. Switching from count to for_each compounds this further: aws_subnet.public[0] and aws_subnet.public["a"] are completely different resource addresses to Terraform, even if you intend them as "the same subnet" - so the migration isn't an in-place update at all, it's destroy count-addressed subnets + create for_each-addressed subnets as entirely separate resources. If the create half runs before the stuck destroy half finishes (or the destroy never finishes because of the DependencyViolation above), the new subnets can end up needing the same CIDR block that the old, still-undeleted subnets already occupy in that VPC - which AWS rejects outright, matching the "CIDR address conflict" you hit. Part 3 - what for_each does differently when a key is deleted: delete the "a" key from var.public_subnets, and Terraform plans to destroy ONLY aws_subnet.public["a"] - "b" is completely untouched, because for_each addresses by key, not position. This is the direct, structural payoff of everything above: with count, ANY reordering touches resources that didn't conceptually change; with for_each, removing one entry only ever touches that one entry, by name, regardless of what else exists in the map or what order it's declared in.

DOUBT_ANSWERS: What is terraform test? :: A built-in Terraform command (terraform test) for writing automated tests against your own .tf configuration, using .tftest.hcl files. Each test file defines one or more run blocks - apply a plan (or a real apply) against given variable values, then assert conditions against the result (for example, checking that an output equals an expected value, or that a resource's attribute matches a pattern) - and terraform test reports pass/fail like any other test runner. It can run against real infrastructure or, since Terraform 1.7, a mocked/overridden provider for fast checks with no AWS calls at all. Not used anywhere on this page's hands-on exercises, which have all been manual plan/apply/curl verification - but it's the real, idiomatic way production Terraform codebases catch a regression (like the copy-paste AZ bug, or a ForceNew surprise) automatically, before a human ever runs apply.
Re-explain the tainted-ALB root cause from the earlier session :: Worth restating cleanly since it's one of the most important mechanics on this page. "Tainted" means Terraform's last attempt to create or update that specific resource did not finish successfully - either AWS itself rejected the call, or the apply was interrupted (Ctrl+C, a closed terminal, a timeout) while that resource's operation was still in flight. Terraform can no longer trust that the resource's real state matches what it tried to do, so it marks it tainted and forces a full destroy-and-recreate on the next apply to get back to a known-good state - this is a SEPARATE mechanism from a normal ForceNew replace (which happens because an attribute changed); a taint happens because a PREVIOUS operation itself failed, regardless of what attributes look like now. In the live incident, the most likely trigger was interrupting an apply during the ALB's normal 2 to 4 minute creation window - that window looks identical to a hang from the terminal, which is exactly what made it feel like a loop. The fix is one of two things: re-apply and let the forced replace run all the way through without interrupting it again (what actually resolved it), or terraform untaint <address> if you've independently confirmed via AWS directly that the resource is actually fine despite the taint flag - never assume that without checking.

HEADING: Variables and count/for_each - and the limits of what plan can protect you from
[P]
Part 1 proved that hardcoding duplicates mistakes. Part 2 proved something sharper: even once every value lives in exactly one place, the SHAPE of how you address resources - count's position versus for_each's key - carries its own real risk, and Terraform's plan output only catches the risks its provider schema was written to anticipate. Everything that actually broke on the real tf2 stack - the count reorder, the count-to-for_each CIDR collision, the -replace cascade - came from the same root cause as every incident in Part 1: a gap between what Terraform's dependency graph can see and what AWS actually enforces.
[BULLETS]
variable, var.name, and terraform.tfvars took every hardcoded value from Part 1 and gave it exactly one home - the AMI id duplication and the copy-paste AZ bug both become structurally harder to make, not just less likely.
count correctly builds N copies fast, but ties each one's identity to its position - reordering a list is indistinguishable, to Terraform, from actually changing what's at that position.
for_each ties identity to a stable key instead, making that specific class of mistake impossible - at the real cost of losing the convenient splat (aws_subnet.public[*].id) and needing a for expression instead.
moved blocks are the missing piece this page didn't have until a real incident forced it: a pure address-rename, written BEFORE a migration starts, costs nothing and touches no real infrastructure - but once a migration is already partway through, it's too late for moved blocks to help, and the honest recovery is one full, carefully reviewed, authoritative apply.
