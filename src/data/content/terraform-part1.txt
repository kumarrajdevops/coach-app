[STAGE knowledge]
HEADING: Same journey, same order, now in Terraform
[P]
Not a new topic — the exact same build you already did by hand with `aws` commands: EC2, then an ASG, then an ALB, then finally a real VPC. This time every resource gets declared once in a `.tf` file instead of typed as a CLI command, and Terraform works out the create order from how resources reference each other. Deliberately no variables, no `count`, no modules yet — just literal values everywhere, so the only thing being learned right now is "how does the thing I already did map onto HCL syntax," one resource type at a time, with a real check after each one before moving to the next.

[STAGE pieces]
HEADING: Provider, resource, data source, state, plan/apply
[DIAGRAM nodes="HCL code (.tf files)|terraform plan|terraform apply|AWS API|Real infrastructure" highlight="terraform plan|terraform apply"]
[DEFS]
Provider :: the plugin that knows how to talk to a specific API — `provider "aws" { region = "us-east-1" }` declared once, configures which account/region every resource in the config talks to.
Resource :: a single infrastructure object you want to exist, declared as `resource "<type>" "<local_name>" { ... }` — an EC2 instance, a VPC, a Security Group. The local name is just how other resources in the SAME config refer to it; it's never sent to AWS.
Data source :: **means:** a read-only lookup of something that already exists, declared as `data "<type>" "<local_name>" { ... }` instead of `resource`. Used below to find your account's existing default VPC and its subnets — Terraform doesn't manage them, it just reads their real IDs so the hardcoded values in this page actually work in your account, not a fake placeholder ID.
State file :: Terraform's own record of exactly what it last created and with what settings — without it, Terraform has no memory of what it already owns, and every `apply` would try to create everything from scratch again.
plan / apply :: `terraform plan` computes the diff between your code, the state file, and the real world (a live API call) — a dry run, nothing changes yet. `terraform apply` executes exactly that diff.
HCL (HashiCorp Configuration Language) :: the declarative syntax `.tf` files are written in. Resources reference each other directly by local name — `aws_instance.web.id`, `aws_lb_target_group.web.arn` — and Terraform automatically works out the correct creation order from those references alone, no manual sequencing.

[STAGE hands-on]
HEADING: EC2, then ASG, then ALB, then VPC — one check after each
[P]
Everything below goes in one working directory. Add each block, run `terraform plan` then `terraform apply`, verify it for real, then move to the next step — don't write all four steps and apply once.
[CODE lang=hcl caption="main.tf - provider, and look up your account's actual default VPC/subnets"]
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"                      # hardcoded on purpose - no variables yet
}

data "aws_vpc" "default" {
  default = true                            # finds your account's real default VPC - no fake ID needed
}

data "aws_subnets" "default" {
  filter {
    name   = "vpc-id"
    values = [data.aws_vpc.default.id]
  }
}
[CODE lang=hcl caption="step 1: EC2 - a Security Group and one instance, exactly like the very first EC2 lesson"]
resource "aws_security_group" "web" {
  name   = "tf1-web-sg"
  vpc_id = data.aws_vpc.default.id

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]             # HTTP from anywhere
  }
  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["203.0.113.5/32"]        # hardcoded to YOUR real public IP, not a placeholder
  }
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_instance" "web" {
  ami                    = "ami-0abcd1234efgh5678"   # a real Amazon Linux 2023 AMI id for your region
  instance_type          = "t3.micro"
  subnet_id              = data.aws_subnets.default.ids[0]
  vpc_security_group_ids = [aws_security_group.web.id]
  associate_public_ip_address = true

  user_data = <<-EOF

resource "aws_autoscaling_group" "web" {
  name                = "tf1-web-asg"
  min_size            = 2
  desired_capacity    = 2
  max_size            = 4

[CODE lang=hcl caption="step 4: a real custom VPC - two public subnets, hardcoded, no count"]
resource "aws_vpc" "main" {
  cidr_block = "10.2.0.0/16"
  tags       = { Name = "tf1-vpc" }
}

resource "aws_subnet" "public_a" {
  vpc_id                  = aws_vpc.main.id
  cidr_block               = "10.2.1.0/24"
  availability_zone        = "us-east-1a"
  map_public_ip_on_launch  = true
  tags = { Name = "tf1-public-a" }
}

resource "aws_subnet" "public_b" {
  vpc_id                  = aws_vpc.main.id
  cidr_block               = "10.2.2.0/24"
  availability_zone        = "us-east-1b"
  map_public_ip_on_launch  = true
  tags = { Name = "tf1-public-b" }
}

resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.main.id
  }
}

resource "aws_route_table_association" "public_a" {
  subnet_id      = aws_subnet.public_a.id
  route_table_id = aws_route_table.public.id
}

resource "aws_route_table_association" "public_b" {
  subnet_id      = aws_subnet.public_b.id
  route_table_id = aws_route_table.public.id
}
[NOTE]
Now update aws_autoscaling_group.web's vpc_zone_identifier, aws_lb.web's subnets, aws_lb_target_group.web's vpc_id, and the Security Group's vpc_id to point at aws_vpc.main instead of the default VPC - this is the same "migrate into a real VPC" step from the VPC page, just expressed as a code change instead of an aws CLI command. Read the rest of this note before you run plan/apply, because this step is NOT a clean "update in place" the way the rest of this page has been - three different kinds of pain are hiding in it, and `terraform plan` will not warn you about any of them in advance.
[BULLETS]
A security group's vpc_id is immutable in AWS - Terraform marks it ForceNew, so this plans as destroy-then-create, by default in that order. Deleting the OLD security group while it's still attached to your live ALB/instances will fail every retry with DependencyViolation and hang indefinitely. Add `lifecycle { create_before_destroy = true }` to aws_security_group.web before you touch vpc_id, so the new one exists (and everything's re-pointed to it) before the old one is destroyed.
A target group's vpc_id is also ForceNew - same create_before_destroy fix applies. But target group names are unique per region+account (not per-VPC like security groups), so a fixed `name` will collide with itself during the create-before-destroy overlap. Switch to `name_prefix` first.
An ALB's subnets are NOT marked ForceNew in the provider schema (changing AZs within the same VPC is a legitimate in-place update) - so pointing them at a different VPC's subnets doesn't plan as a replacement at all. Terraform will attempt a quiet in-place update, and AWS will reject it at apply time, not at plan time. The only way to actually move an ALB to a new VPC is to force a real replacement yourself: `terraform apply -replace="aws_lb.web"`.
Even after all three of those are fixed, your ASG's already-running instances will NOT move to the new VPC just because vpc_zone_identifier changed - EC2 instances can't move between VPCs. They keep running under their original launch template/security group until something replaces them (a deliberate instance refresh, or cycling desired_capacity through 0).

[P]
Nothing catches this automatically. You'd only notice by actually reading the plan output's availability_zone values carefully, or by checking afterward with:
[CODE lang=bash caption="the only way to actually catch it"]
aws ec2 describe-subnets --filters Name=vpc-id,Values=<vpc-id> \
  --query 'Subnets[*].[SubnetId,AvailabilityZone]' --output table
# Both rows show the same AZ - the "multi-AZ" ASG/ALB setup you THINK you built
# is actually single-AZ, silently, with no error anywhere in the apply

[STAGE key-insight]
HEADING: Hardcoding doesn't just duplicate values - it duplicates mistakes
[NOTE]
Terraform validates that your HCL is syntactically correct and that resource arguments are the right type - it does not validate that two "different" blocks are actually different in the way you intended. Copy-pasting a block and editing some but not all of the literal values is a real, common, completely silent failure mode - the exact kind of bug that's invisible until you specifically go looking for it. This is the honest motivation for Part 2: every hardcoded value that appears more than once (the AMI id in the launch template, now also still sitting in a leftover note from step 1; the availability zones repeated across subnet and route-table-association blocks) is a place a future edit can silently diverge. Variables and `count`/`for_each` don't just save typing - they make this specific class of mistake structurally impossible, because there's only one place the value is ever written.

[STAGE key-insight]
HEADING: Round 1's clarification, in plain terms
[NOTE]
Adding a third subnet, the hardcoded way: think of each subnet as a parking spot you're painting onto a lot by hand, one at a time. Adding a third spot means painting the new spot itself (a new aws_subnet block), then painting the line connecting that spot to the exit road so cars can actually use it (a new aws_route_table_association - when you're doing this by hand instead of letting a tool draw it automatically, every spot needs its own connecting line). Then you tell the two things that route traffic to spots "you can also use this new one now" - once to the ASG (add it to vpc_zone_identifier), once to the ALB (add it to subnets). You don't need to touch the target group or the route table/gate itself - the target group's more like a phone directory than a parking location (it doesn't care which spot a car's in), and one exit gate can serve any number of spots without needing its own copy per spot.
[NOTE]
The duplicated AMI id: it's like writing someone's phone number by hand on two separate forms instead of saving it once in a shared contacts list. If that person's number changes, you have to remember to update both forms - and if you only update one, nothing tells you the two forms now disagree. Same thing here: the AMI id is typed out twice (once in the old single-instance example, once in the launch template). If AWS releases a newer, patched image and you update one copy but forget the other, nothing warns you - Terraform just sees two separate, individually valid pieces of text. It has no idea they were ever supposed to match.

# -replace is a CLI flag, not something you can write into the resource block -
# ForceNew is the provider author's choice per attribute, not yours to set from HCL
[CODE lang=bash caption="cycling an ASG through zero to force-retire stale instances (fault 5)"]
# 1. edit main.tf: min_size = 0, desired_capacity = 0
terraform apply
# 2. edit main.tf back: min_size = 2, desired_capacity = 2
terraform apply
# every instance is now on the current launch template - nothing left pinning the old SG
[NOTE]
The common thread across faults 2-4: `terraform plan` only knows what the provider's schema tells it to check. A security group's vpc_id is correctly marked ForceNew, so plan warns you. An ALB's subnets are deliberately NOT marked ForceNew - because for the overwhelmingly common case (adding an AZ within the same VPC) that's a legitimate, safe in-place update, and marking it ForceNew would force a full ALB rebuild on every ordinary AZ change for every other user of that resource. The schema is right for the common case and silently wrong for yours. Plan passing is not proof AWS will accept the change - it's proof Terraform's local type-checking passed.

CLARIFICATION: Full answer for the record. Part 1 - aws_security_group.vpc_id is ForceNew because a security group's VPC is permanently fixed at creation; there's no legitimate reason to ever change it in place, so marking it ForceNew costs nothing. aws_lb.subnets is NOT ForceNew because changing subnets is a routine, safe, in-place operation in the overwhelming majority of real usage - adding or removing an AZ within the SAME VPC. The schema attribute is one static flag; it can't distinguish "same VPC, different AZ" from "an entirely different VPC" - both just look like "the subnets list changed." If subnets were ForceNew to catch your migration case, every ordinary AZ change for every aws_lb user would force a full destroy-and-recreate, and - as you correctly identified - that means a brand-new DNS name every time, breaking anything depending on the ALB's DNS staying stable. The provider protects the common case and lets the rare, genuinely-impossible-in-place case (moving VPCs) fail loudly at apply instead of being caught at plan. Part 2 - Terraform's dependency graph is built from the resources and references present in the CURRENT config being planned. A resource still present in config (like aws_security_group.web with create_before_destroy) has real edges in that graph, so anything referencing it gets correctly sequenced before it's touched. A resource deleted from config entirely has no such edges to build from - nothing tells the graph "this old thing is still attached to a live ALB/instance in actual AWS." That's the actual boundary: trust Terraform's ordering for resources still present and referenced; don't trust it for a resource you've just removed from config while something else might still be using it in reality - verify directly and split into separate -target applies instead.

[STAGE key-insight]
HEADING: Round 2's clarification, in plain terms
[NOTE]
Why the ALB didn't get a warning but the security group did: think of a security group's VPC like the address printed on your ID card - it's permanently fixed the moment it's made. There's no editing it; you have to get a whole new card issued. Terraform knows this rule, so when you try to change it, it warns you upfront - this needs a brand new one. Now think of an ALB's subnets like which rooms of a house it's plugged into. Normally you just move the plug to a different room in the same house - totally routine, that's "adding an availability zone." Terraform assumes that's always what's happening, because most of the time it is. It has no way to notice "wait, this time you're moving the plug to a completely different house" (a different VPC) - so it tries anyway, and the real wiring (AWS) only refuses the connection at the very last second, during apply. Why didn't they just make subnets strict too? Because then even the everyday harmless case - adding a room in the same house - would force AWS to tear the whole ALB down and rebuild it, and tearing it down means a brand-new DNS name every time, breaking anything that had the old one saved somewhere. So the tradeoff was: keep the common case easy, and let the rare "move to a totally different house" case fail late instead.
[NOTE]
Why you can't fully trust the ordering once something's deleted from the file: Terraform draws its whole "do this before that" map by looking only at your current .tf file and asking "what points to what." If a resource is still written in the file and something references it, Terraform sees the arrow clearly and gets the order right. But the second you delete that resource from the file entirely, the arrow disappears too - as far as Terraform's map is concerned, nothing uses it anymore. It doesn't go check real AWS first to ask "is something still actually plugged into this?" So it can try to delete it too early, even though in reality your ALB is still using it. The rule of thumb: trust Terraform's ordering when a resource is still in the file and referenced. Don't trust it the moment you've deleted that resource - check it yourself.

Does apply/destroy only create or update terraform.tfstate? :: Yes, mechanically correct. Every apply or destroy rewrites `terraform.tfstate` to reflect the new truth, and keeps exactly one prior copy as `terraform.tfstate.backup` (the state as it was immediately before that operation). It's a two-generation system, not a running history.
Is the "serial" number in terraform.tfstate always odd? :: No, that's coincidence - checked your actual file just now: current serial is 89, backup is 87. `serial` is just a counter incremented every time Terraform writes state - it has no odd/even significance, it's purely "how many times has state been written in this lineage so far."
Between apply and destroy, is it only current state plus one backup generation, no deeper history? :: Correct, confirmed against your actual files. Locally, Terraform only ever keeps two generations - current and one-back. Real history (every version, forever) only exists with a backend that supports versioning, like an S3 bucket with versioning enabled, or Terraform Cloud's built-in state history.
If terraform.tfstate is deleted, only an older .backup exists, and the .tf files are gone too - what happens? :: Two problems stacked together. Your `.backup` reflects state from *before* the destroy - if the real infrastructure is actually gone, restoring it makes Terraform believe things exist that don't, causing confusing diffs (usually harmless, since AWS just reports them missing and Terraform drops them from state). Bigger problem: with the `.tf` files gone too, there's no config at all - state alone is useless without it. The only ways back: restore the `.tf` files from git or a backup, or start fresh and use `terraform import` to re-adopt whatever's actually still running, one resource at a time.
What does protocol = "-1" mean? :: AWS's own literal convention for "all protocols" - a wildcard, not a Terraform invention. It's exactly what you'd see in the raw AWS API/CLI (`IpProtocol: "-1"`) for the same rule. "Note: You didn't use the -out option..." - what does that mean? :: It's warning about a gap between planning and applying - real AWS state could in theory change between when you review a plan and when you apply it. `terraform plan -out=myplan` freezes the exact computed plan to a file, and `terraform apply "myplan"` guarantees it applies precisely that plan, erroring instead of silently recomputing if anything's drifted. Plain `terraform apply` always recomputes its own fresh plan live - fine solo, but in a team/CI setting that gap is exactly how "it looked safe when I reviewed it" surprises happen. HEADING: Five tools, one decision flow - a quick reference before you practice
[P]
Keep this open while you work through the migration below. None of these five are interchangeable - each answers a different question at a different point in the same workflow.
[TABLE]
Tool | Use it when | Today's real example
ForceNew | Not something you set - read it from `terraform plan` output to predict whether a change destroys-and-recreates or updates in place. `-/+` or a `# forces replacement` comment means ForceNew; a plain `~` means it isn't - even when you expected it to be. | `aws_security_group.vpc_id` showed `-/+`. `aws_lb.subnets` showed only `~` - the actual trap.
`lifecycle { create_before_destroy = true }` | Plan shows `-/+` on a resource that something else is still actively attached to right now. Add it before applying, not after getting stuck. | `aws_security_group.web`'s vpc_id change.
`name_prefix` instead of `name` | `create_before_destroy` is in play and the resource's naming uniqueness is broader than per-VPC (region or account-scoped, not VPC-scoped). | `aws_lb_target_group` - a fixed name would collide with itself during the brief overlap.
`-target` | Force an order Terraform's own graph won't guarantee, or retry just one piece of a stuck or partial apply. Not for routine use - needing it every apply means your config's dependencies aren't really expressing what you think they are. | Detaching the ALB from its old SG before destroying that SG; later, scaling the ASG through 0 without touching anything else.
`-replace` | Plan shows a harmless `~ update in-place`, but you know AWS will actually reject it, because the attribute isn't ForceNew in the schema even though your specific change needs it to be. Use narrowly - forcing a replace on something that could update cleanly is wasteful, and for some resources (like an ALB) means losing something stable, like its DNS name. | Moving `aws_lb.web`'s subnets across VPCs.
[NUMBERED]
The actual decision flow, in order: change the attribute, then run terraform plan.
Does plan show -/+ replace? That's ForceNew. Ask: is the old resource still actively used by something else right now? If yes, add create_before_destroy (plus name_prefix if the naming is broader than per-VPC) before you apply.
Does plan show a plain ~ update in-place, but you know better than the schema does? That's your signal to use -replace explicitly.
Does a destroy ever hang, or does the ordering go wrong anyway? Stop the apply safely, then use -target to split the work into a correctly-sequenced pair of applies.

[STAGE conclusion]
HEADING: Two working stacks, one hard-won set of rules
[P]
Everything in Terraform's own vocabulary from here on maps directly onto something you actually did, twice: a provider talking to one AWS account; resources for every piece of EC2/ASG/ALB/VPC you already built by hand with the CLI; a state file that remembered all of it across two separate stacks (tf1 and tuf) without you ever re-typing an ID; a plan that mostly told the truth, except for the one place its own schema couldn't see your intent.
[BULLETS]
tf1 went from a single hardcoded EC2 instance to a full ASG-behind-an-ALB stack, then migrated whole into a custom VPC - and broke, for real, in five distinct ways along the way.
Every one of those five failures came from the same root cause wearing a different costume: Terraform's plan only knows what the provider's schema tells it to check, and AWS's actual API is the only thing that enforces the rest.
tuf repeated the same migration with one upgrade - private subnets behind a NAT Gateway, the ALB and the instances finally on separate security groups - applying every fix from the table yourself instead of being walked through it.
Nothing here used a single variable, a single `count`, or a single module. Every AMI id, every CIDR block, every subnet's availability zone was typed out by hand, more than once in places - which is exactly what made the copy-paste AZ bug and the duplicated AMI id real, visible risks instead of abstract warnings.
[NOTE]
Part 2 picks up exactly where this leaves off: turning every one of those hand-typed, duplicated values into variables, and the repeated per-subnet blocks (subnets, route table associations, the pattern you hit again building tuf's four subnets by hand) into `count`/`for_each`. You now have first-hand proof of what that duplication actually costs when it goes wrong - Part 2 is about making that specific class of mistake structurally impossible instead of just risky.
