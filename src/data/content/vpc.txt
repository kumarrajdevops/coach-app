[STAGE knowledge]
HEADING: The layer under everything you've already built
[P]
Three pages, and you've typed `--vpc-zone-identifier subnet-aaa,subnet-bbb`, `vpc-0123456789abcdef0`, and `0.0.0.0/0` more times than you can count — without ever being told what any of it actually *is*, and every EC2/ASG/ALB setup you've built so far has been sitting quietly in AWS's **default VPC**, not one you built yourself. A classic real interview trap lives exactly here: "my Security Group is wide open, my ALB shows healthy targets, I still can't reach the site from the internet." That's not a permissions problem, and no amount of staring at Security Group rules fixes it — it's a routing problem, one layer below everything you've touched so far. By the end of this page you'll have built a real custom VPC from scratch, with both public and private subnets, and migrated your actual running ASG and ALB into it — which is exactly where a real Security Group gotcha is waiting for you.

[STAGE pieces]
HEADING: VPC, subnets, Internet Gateway, route tables, NAT, NACLs
[DIAGRAM nodes="Internet|Internet Gateway|VPC|Public Subnet|Private Subnet|EC2 instance" highlight="Internet Gateway|Public Subnet|Private Subnet"]
[DEFS]
VPC (Virtual Private Cloud) :: your own private, isolated slice of AWS network space, defined by a CIDR block (e.g. `10.0.0.0/16`). Every EC2 instance, ALB, and ASG you've built so far has been living in AWS's *default* VPC — you just never saw it directly, only its ID.
Subnet :: a slice of the VPC's address range, tied to exactly one Availability Zone. This is why the ASG and ALB pages both asked for multiple subnet IDs — spanning AZs is what multi-AZ resilience actually means at the networking level, not just an ASG setting.
Internet Gateway (IGW) :: the VPC's one door to the public internet. Attached once per VPC. By itself it does nothing — nothing routes through it unless something explicitly tells it to.
Route table :: **means:** the actual rules that decide where a subnet's outbound traffic goes. This is the single most important definition on this page — a subnet is "public" or "private" *only* because of which route table is attached to it, never because of some inherent subnet property or a checkbox you ticked at creation.
Public vs. private subnet :: a subnet is **public** if and only if its route table has a route sending `0.0.0.0/0` traffic to the Internet Gateway. A subnet is **private** if its route table has no such route — full stop, regardless of anything else about it. Two subnets can look identical and one is public, one is private, purely because of which route table got associated with each.
NAT Gateway :: lets instances in a *private* subnet reach *out* to the internet (package updates, API calls) without being reachable *from* the internet. It sits in a public subnet itself, needs its own Elastic IP; a private subnet's route table points its `0.0.0.0/0` traffic at the NAT Gateway instead of the IGW — outbound works, inbound from the internet still doesn't.
Network ACL (NACL) :: a firewall at the *subnet* boundary, not the instance boundary like a Security Group. The critical difference: a NACL is **stateless** — unlike a Security Group, which automatically allows return traffic for anything it let in, a NACL needs separate, explicit inbound *and* outbound rules for both directions of every connection, including an explicit rule for the ephemeral port range (1024-65535) so reply traffic isn't silently dropped. Rules are evaluated in number order, lowest first, first match wins.

[STAGE hands-on]
HEADING: Building the real pattern: public + private subnets, NAT, and a NACL
[P]
Every `vpc-...` and `subnet-...` from the last three pages was a placeholder living in the default VPC. This builds the real thing — the full pattern, not just the public-subnet slice.
[CODE lang=bash caption="1. create the VPC itself"]
aws ec2 create-vpc --cidr-block 10.0.0.0/16 \
  --query 'Vpc.VpcId' --output text          # note the returned vpc-id, everything below needs it
[CODE lang=bash caption="2. two PUBLIC subnets, one per AZ"]
aws ec2 create-subnet --vpc-id <vpc-id> --cidr-block 10.0.1.0/24 \
  --availability-zone us-east-1a --query 'Subnet.SubnetId' --output text
aws ec2 create-subnet --vpc-id <vpc-id> --cidr-block 10.0.2.0/24 \
  --availability-zone us-east-1b --query 'Subnet.SubnetId' --output text
[CODE lang=bash caption="3. two PRIVATE subnets, one per AZ - for anything that should never be internet-reachable"]
aws ec2 create-subnet --vpc-id <vpc-id> --cidr-block 10.0.11.0/24 \
  --availability-zone us-east-1a --query 'Subnet.SubnetId' --output text
aws ec2 create-subnet --vpc-id <vpc-id> --cidr-block 10.0.12.0/24 \
  --availability-zone us-east-1b --query 'Subnet.SubnetId' --output text
[CODE lang=bash caption="4. create and attach an Internet Gateway"]
aws ec2 create-internet-gateway --query 'InternetGateway.InternetGatewayId' --output text
aws ec2 attach-internet-gateway --vpc-id <vpc-id> --internet-gateway-id <igw-id>
[CODE lang=bash caption="5. public route table: route 0.0.0.0/0 to the IGW, associate both public subnets"]
aws ec2 create-route-table --vpc-id <vpc-id> --query 'RouteTable.RouteTableId' --output text
aws ec2 create-route --route-table-id <public-rtb-id> \
  --destination-cidr-block 0.0.0.0/0 --gateway-id <igw-id>   # this one line is what makes it a "public" route table
aws ec2 associate-route-table --subnet-id <public-subnet-1> --route-table-id <public-rtb-id>
aws ec2 associate-route-table --subnet-id <public-subnet-2> --route-table-id <public-rtb-id>
aws ec2 modify-subnet-attribute --subnet-id <public-subnet-1> --map-public-ip-on-launch
aws ec2 modify-subnet-attribute --subnet-id <public-subnet-2> --map-public-ip-on-launch
[CODE lang=bash caption="6. a NAT Gateway in one public subnet, with its own Elastic IP"]
aws ec2 allocate-address --domain vpc --query 'AllocationId' --output text
aws ec2 create-nat-gateway --subnet-id <public-subnet-1> --allocation-id <eip-allocation-id> \
  --query 'NatGateway.NatGatewayId' --output text
# Wait for it to reach "available" state before using it in a route:
aws ec2 describe-nat-gateways --nat-gateway-ids <nat-gw-id> --query 'NatGateways[0].State' --output text
[CODE lang=bash caption="7. private route table: route 0.0.0.0/0 to the NAT Gateway, associate both private subnets"]
aws ec2 create-route-table --vpc-id <vpc-id> --query 'RouteTable.RouteTableId' --output text
aws ec2 create-route --route-table-id <private-rtb-id> \
  --destination-cidr-block 0.0.0.0/0 --nat-gateway-id <nat-gw-id>   # outbound-only, never inbound-reachable
aws ec2 associate-route-table --subnet-id <private-subnet-1> --route-table-id <private-rtb-id>
aws ec2 associate-route-table --subnet-id <private-subnet-2> --route-table-id <private-rtb-id>
[CODE lang=bash caption="8. a custom NACL for the public subnets - explicit both-direction rules, unlike a Security Group"]
aws ec2 create-network-acl --vpc-id <vpc-id> --query 'NetworkAcl.NetworkAclId' --output text
# Inbound: web traffic, SSH from you only, and ephemeral ports for YOUR OWN outbound replies
aws ec2 create-network-acl-entry --network-acl-id <nacl-id> --rule-number 100 --protocol tcp \
  --port-range From=80,To=80 --cidr-block 0.0.0.0/0 --rule-action allow --ingress
aws ec2 create-network-acl-entry --network-acl-id <nacl-id> --rule-number 110 --protocol tcp \
  --port-range From=22,To=22 --cidr-block <your-ip>/32 --rule-action allow --ingress
aws ec2 create-network-acl-entry --network-acl-id <nacl-id> --rule-number 120 --protocol tcp \
  --port-range From=1024,To=65535 --cidr-block 0.0.0.0/0 --rule-action allow --ingress
# Outbound: replies to inbound 80/22 traffic use ephemeral destination ports;
# the instance's own outbound calls (e.g. dnf update) need 80/443 explicitly allowed out
aws ec2 create-network-acl-entry --network-acl-id <nacl-id> --rule-number 100 --protocol tcp \
  --port-range From=1024,To=65535 --cidr-block 0.0.0.0/0 --rule-action allow --egress
aws ec2 create-network-acl-entry --network-acl-id <nacl-id> --rule-number 110 --protocol tcp \
  --port-range From=80,To=80 --cidr-block 0.0.0.0/0 --rule-action allow --egress
aws ec2 create-network-acl-entry --network-acl-id <nacl-id> --rule-number 120 --protocol tcp \
  --port-range From=443,To=443 --cidr-block 0.0.0.0/0 --rule-action allow --egress
[CODE lang=bash caption="find each public subnet's CURRENT association id before you can replace it"]
aws ec2 describe-network-acls --filters Name=vpc-id,Values=<vpc-id> \
  --query 'NetworkAcls[].Associations[].[NetworkAclAssociationId,SubnetId,NetworkAclId]' --output table
# Every subnet starts associated with the VPC's default (allow-all) NACL - the
# association-id below is THAT association, not your new custom NACL's id.
# Copy the NetworkAclAssociationId for each public subnet from this table.
[CODE lang=bash caption="swap each public subnet onto your new custom NACL"]
aws ec2 replace-network-acl-association --association-id <public-subnet-1-current-assoc-id> --network-acl-id <nacl-id>
aws ec2 replace-network-acl-association --association-id <public-subnet-2-current-assoc-id> --network-acl-id <nacl-id>
[NOTE]
Cost awareness: a NAT Gateway bills hourly plus per-GB processed, even idle — tear it down (`aws ec2 delete-nat-gateway`) and release the Elastic IP when you're done experimenting. Production setups often run one NAT Gateway per AZ for resilience; this page uses one to keep cost down while you're learning, same trade-off called out in the ASG pricing discussion. Also: every `--cidr-block`/`--availability-zone` flag above is required by the API — a command missing one (e.g. create-subnet without `--cidr-block`) fails fast with a clear `MissingParameter` error, not a silent default.

[STAGE troubleshoot]
HEADING: Moving the real ASG into the new VPC
[P]
Time to actually migrate. The Security Group hasn't changed — same two rules, port 80 open, port 22 restricted to you — so there's no reason to touch it, right? Just point the ASG at the new public subnets:
[CODE lang=bash caption="the migration attempt - this is rejected immediately, not after a failed launch"]
aws autoscaling update-auto-scaling-group --auto-scaling-group-name web-asg \
  --vpc-zone-identifier "<public-subnet-1>,<public-subnet-2>"
# aws: [ERROR]: An error occurred (ValidationError) when calling the
# UpdateAutoScalingGroup operation: One or more security groups in the launch
# template are not linked to the VPCs configured in the Auto Scaling group
[P]
Worth noticing exactly what kind of failure this is: AWS validates the launch template's Security Group against the new subnets' VPC *synchronously*, at the API call itself — the update is flatly rejected before any instance ever attempts to launch. No wasted launch attempts, no need to dig through scaling activity history for this one; the error comes back immediately, in the same terminal command.
[CODE lang=bash caption="confirm why, directly"]
aws ec2 describe-security-groups --group-ids <old-sg-id> --query 'SecurityGroups[0].VpcId' --output text
# Returns the OLD (default) VPC's id - not the new one you just built. The SG
# genuinely does not exist from the new VPC's point of view, rules or no rules.

[STAGE key-insight]
HEADING: Two things that aren't what they look like
[NOTE]
Same root lesson as the route-table step above, now hitting a resource you thought was already finished: **Security Groups, target groups, and NACLs are all scoped to exactly one VPC.** An SG isn't a global, reusable set of firewall rules you can point anywhere — it's an object that lives inside one specific VPC's boundary, full stop. Moving compute to a new VPC always means recreating every VPC-scoped resource it depends on, even when the rules themselves are byte-for-byte identical to what you had before. This is exactly why "just change the subnet IDs" is never the whole migration.
[NOTE]
A target group specifically isn't just VPC-scoped — it has **no subnet or public/private property of its own at all**. The ALB genuinely sits in subnets (real network interfaces, placed where you tell it). A target group doesn't sit anywhere — it's a logical registry (a list of target IDs/IPs plus health-check config) tied to a VPC so it knows what it's allowed to point at, nothing more. What's actually public or private is only ever the ALB's own placement and the targets' own placement — in this build, ALB in the public subnets, EC2 targets in the private ones, with the target group just pointing between them. The giveaway in Terraform later: `aws_lb_target_group` takes a `vpc_id`, never a `subnet_ids` argument — there's nothing to place.

DOUBT_ANSWERS: Can services be moved from one VPC to another? :: Not directly "moved" — almost everything VPC-scoped (Security Groups, subnets, target groups, NACLs) has to be recreated in the destination VPC. What actually moves is your compute getting re-registered against the new resources, exactly what you just did. There's no single "move VPC" button for an existing resource.
Is a VPC different per region, and can I have 2 VPCs in one region? :: A VPC lives entirely within ONE AWS region — its subnets can span multiple AZs in that region, but a VPC itself never crosses regions. Yes, you can create many VPCs in a single region (default soft limit is 5 per region per account, raisable on request).
How do I connect an EC2 in one VPC/region to an EC2/RDS in another VPC/region? :: VPC Peering is the simplest answer at this stage — a direct 1:1 connection, works same-region or cross-region, but is not transitive (peering A-B and B-C does not let A reach C). Transit Gateway is the scalable version once you have many VPCs to connect, hub-and-spoke instead of one peering link per pair.
Explain IPv4 CIDR, and why does everything start with 10.0.0.x? :: CIDR is `IP/prefix-length` notation — the prefix length is how many leading bits are fixed (the "network" part); the rest vary (the "host" part). `10.0.0.0/8` is one of three IANA-reserved PRIVATE ranges (RFC 1918, alongside `172.16.0.0/12` and `192.168.0.0/16`) — never routable on the public internet. That's exactly why `10.x.x.x` is the standard convention for VPC CIDRs, not an AWS-specific requirement.
Explain tenancy :: `default` = your instances share physical hardware with other AWS customers (standard, what you've used everywhere so far, VM-level isolation). `dedicated` = hardware reserved for your AWS account only, costs more. `host` (Dedicated Host) = an actual specific physical server you control placement on, mainly needed for license models tied to physical cores (e.g. some Windows/Oracle licensing).
/24 = 256 IPs, /20 = 4096 IPs - explain, what's the cost for more IPs, and why 256 becomes 251 usable :: Fewer fixed bits means more host bits means more addresses: /24 leaves 8 variable bits (2^8 = 256), /20 leaves 12 (2^12 = 4096) - a smaller prefix NUMBER means a BIGGER subnet, which trips people up since it feels backwards. There's no AWS cost for subnet size itself - you're reserving address space, not paying for it; cost comes from the actual resources you run inside it. AWS reserves 5 addresses in every subnet: network address (.0), VPC router (.1), DNS (.2), reserved for future use (.3), and broadcast (.255) - 256 minus those 5 reserved = 251 usable.
Why can't a subnet's Availability Zone be edited after creation? :: The AZ is fixed at creation because the subnet's physical placement is tied to that specific AZ at the infrastructure level - the same category of constraint as not being able to move an EBS volume between AZs without a snapshot/restore. To "change" a subnet's AZ you delete it and create a new one.
Why are there 2 route tables - main=yes and the one I created (main=no)? :: Every VPC gets exactly one implicit "main" route table automatically at creation - any subnet NOT explicitly associated with a different route table silently falls back to it. The public and private route tables you built by hand are both main=no, custom ones. This matters in practice: forget to explicitly associate a brand-new subnet with one of your custom route tables, and it quietly falls back to the main one - if that has no IGW route, the subnet is accidentally private with zero error or warning.
What happens if --map-public-ip-on-launch isn't set on a public subnet? :: Instances launched there won't get a public IP automatically, even though the subnet's route table can reach the internet fine - route capability and actually having a public IP are two separate things. You'd need to pass `--associate-public-ip-address` per instance at launch time (like the very first manual EC2 lesson), or attach an Elastic IP afterward.
Explain ingress/egress, rule-numbers, and the 1024-65535 range :: `--ingress`/`--egress` pick which direction of traffic a NACL rule applies to. `rule-number` sets evaluation order - a NACL checks rules lowest-number-first and stops at the first match, unlike a Security Group where every matching rule is just OR'd together with no ordering at all; leaving gaps (100, 110, 120) is deliberate, so you can insert a new rule later without renumbering everything. `1024-65535` is the ephemeral port range operating systems assign to the "other side" of a connection - since NACLs are stateless, you must explicitly allow this range or reply traffic to a legitimate request gets silently dropped.
When is the default NACL (acl-0fb2...) created, and what's it for? :: Every VPC gets a default NACL automatically at creation, the same idea as the implicit main route table. Unlike a custom NACL (which starts deny-by-default until you add allow rules), the default NACL allows ALL traffic in both directions - every subnet starts associated with it until you explicitly swap it out, which is exactly the association you had to look up and replace via describe-network-acls.
Explain the ValidationError in detail :: AWS checks, at the exact moment you call `update-auto-scaling-group`, whether the launch template's Security Group(s) belong to the SAME VPC as the subnets you're setting. If not, it rejects the entire call immediately with this ValidationError, before attempting to launch a single instance. This is actually a correction to how the lesson originally described this failure (as something surfacing later via scaling activities) - your real test showed AWS catches it earlier and more cleanly than that, and the module's content has been corrected to match.
I used VPC/subnets at SG, ASG, TG, ALB but not the launch template - is that mandatory? :: A launch template has no explicit "VPC" field of its own - which subnet(s) it ends up launching into is entirely controlled by whichever ASG uses it, via that ASG's own `--vpc-zone-identifier`, never hardcoded in the template itself. That's deliberate: it lets one launch template be reused across different ASGs or subnets. DOUBT_ANSWERS: What's the difference between 502, 503, and 504, and should I only watch for Timeout errors? :: No — each one points at a different layer, and conflating them (your "503 Gateway timeout" merges two separate codes) costs you the diagnostic value of the distinction. **502 Bad Gateway**: the ALB reached a target and got back an invalid/malformed response, or the connection was reset mid-request — look at the TARGET's own behavior (this is the churn-window case from the ALB page). **503 Service Unavailable**: the ALB has NO targets to even attempt routing to right now — zero registered/available targets, exactly what you saw when instances were deleted manually faster than replacements registered — look at TARGET GROUP MEMBERSHIP/capacity, not the targets themselves. **504 Gateway Timeout**: the ALB forwarded the request and then waited for a reply that never came, until it gave up — look at the NETWORK PATH between ALB and target. This is actually the technically correct label for what fault A produced: the NACL was silently dropping the reply packets, so the ALB wasn't refused and wasn't told "no targets" - it just never got an answer and eventually timed out. "503 Gateway timeout" isn't a real distinct AWS code; what you hit was 504, and the fact that it was a timeout (not an instant refusal) is itself evidence the problem was a silent network-level drop, same hang-vs-refused distinction from the very first EC2 lesson, now one more layer up the stack.
