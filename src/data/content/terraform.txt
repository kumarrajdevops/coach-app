[STAGE knowledge]
HEADING: Could you rebuild the last 4 pages from memory, right now?
[P]
Four pages, dozens of `aws` commands, typed by hand, in exactly the right order — a VPC, four subnets, an Internet Gateway, two route tables, a NAT Gateway, a custom NACL with six rules, a Security Group, a launch template, an ASG, a target group, an ALB, a listener. Could you reproduce that exact setup again right now, from memory, without scrolling back through your own command history? Almost certainly not reliably — and that's not a knowledge gap, it's the actual problem Infrastructure as Code exists to solve. Terraform lets you describe the end state you want, once, declaratively, in files you can version and review like any other code — and the tool itself works out the exact sequence of create/update/destroy API calls needed to get there, every time, identically.

[STAGE pieces]
HEADING: Provider, resource, state, plan/apply, HCL
[DIAGRAM nodes="HCL code (.tf files)|terraform plan|terraform apply|AWS API|Real infrastructure" highlight="terraform plan|terraform apply"]
[DEFS]
Provider :: the plugin that knows how to talk to a specific API — `provider "aws" { region = "us-east-1" }` declared once, configures which account/region every resource in the config talks to.
Resource :: a single infrastructure object you want to exist, declared as `resource "<type>" "<local_name>" { ... }` — an EC2 instance, a VPC, a Security Group. The local name is just how other resources in the SAME config refer to it; it's not sent to AWS.
State file :: **means:** Terraform's own record of exactly what it last created and with what settings — the durable, versionable memory that the knowledge step's "could you rebuild this from memory" problem actually gets solved by. Without state, Terraform has no idea what it already owns, and every `apply` would try to create everything from scratch again.
plan / apply :: `terraform plan` computes the diff between your code, the state file, and the real world (a live API call) — a dry run, nothing changes yet. `terraform apply` executes exactly that diff, nothing more and nothing less.
Variables and outputs :: `variable` blocks parameterize a config (so the same code can target dev vs prod with different values); `output` blocks expose a value after apply — e.g. the ALB's DNS name — for you to read or for another config to consume.
HCL (HashiCorp Configuration Language) :: the declarative syntax `.tf` files are written in. Resources reference each other directly by local name — `aws_instance.web.id`, `aws_lb_target_group.web.arn` — and Terraform automatically works out the correct creation order from those references, no manual sequencing needed.

[STAGE hands-on]
HEADING: Reproducing the EC2/ASG/ALB/VPC stack as real Terraform code
[P]
A fresh, parallel stack — not touching the real infrastructure from the last 4 pages, so there's zero risk to what's actually running. Organized into real project files, the way an actual Terraform repo looks, not one giant file.
[CODE lang=hcl caption="providers.tf"]
terraform {
  required_version = ">= 1.5.0"            # pins the CLI version so everyone runs compatible behavior
  required_providers {
    aws = {
      source  = "hashicorp/aws"            # the official AWS provider
      version = "~> 5.0"                   # allow any 5.x, pin the major version
    }
  }
}

provider "aws" {
  region = var.aws_region                  # every resource below is created in this region
}
[CODE lang=hcl caption="variables.tf"]
variable "aws_region" {
  type    = string
  default = "us-east-1"
}

variable "vpc_cidr" {
  type    = string
  default = "10.1.0.0/16"                  # 10.1.x.x - deliberately different from the hand-built 10.0.x.x stack
}

variable "azs" {
  type    = list(string)
  default = ["us-east-1a", "us-east-1b"]
}

variable "your_ip" {
  type        = string
  description = "your current public IP, for SSH - get it with curl ifconfig.me"
}

variable "key_name" {
  type        = string
  description = "an existing EC2 key pair name in this account"
}

variable "ami_id" {
  type        = string
  description = "an Amazon Linux 2023 AMI id for your region"
}
[CODE lang=hcl caption="vpc.tf - VPC, subnets, IGW, NAT, route tables"]
resource "aws_vpc" "main" {
  cidr_block = var.vpc_cidr
  tags       = { Name = "tf-web-vpc" }
}

resource "aws_subnet" "public" {
  count             = 2                              # creates 2 subnets from one block - public[0] and public[1]
  vpc_id            = aws_vpc.main.id
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, count.index)        # 10.1.0.0/24, 10.1.1.0/24
  availability_zone = var.azs[count.index]
  map_public_ip_on_launch = true
  tags = { Name = "tf-public-${count.index}" }
}

resource "aws_subnet" "private" {
  count             = 2
  vpc_id            = aws_vpc.main.id
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, count.index + 10)   # 10.1.10.0/24, 10.1.11.0/24
  availability_zone = var.azs[count.index]
  tags = { Name = "tf-private-${count.index}" }
}

resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id
  tags   = { Name = "tf-igw" }
}

resource "aws_eip" "nat" {
  count  = 2                                          # one Elastic IP per NAT Gateway, one per AZ
  domain = "vpc"
}

resource "aws_nat_gateway" "main" {
  count         = 2
  subnet_id     = aws_subnet.public[count.index].id   # NAT Gateway lives in the public subnet
  allocation_id = aws_eip.nat[count.index].id
  tags          = { Name = "tf-nat-${count.index}" }
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.main.id          # this is what makes it the "public" route table
  }
  tags = { Name = "tf-public-rtb" }
}

resource "aws_route_table" "private" {
  count  = 2                                           # one private route table per AZ - matches its own NAT
  vpc_id = aws_vpc.main.id
  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.main[count.index].id
  }
  tags = { Name = "tf-private-rtb-${count.index}" }
}

resource "aws_route_table_association" "public" {
  count          = 2
  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id
}

resource "aws_route_table_association" "private" {
  count          = 2
  subnet_id      = aws_subnet.private[count.index].id
  route_table_id = aws_route_table.private[count.index].id
}
[CODE lang=hcl caption="security.tf - Security Group (the NACL is left as a stretch exercise for Round 1)"]
resource "aws_security_group" "web" {
  name   = "tf-web-sg"
  vpc_id = aws_vpc.main.id

  ingress {
    description = "HTTP from anywhere"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
  ingress {
    description = "SSH from you only"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["${var.your_ip}/32"]
  }
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"                                # -1 = all protocols/ports, standard default-allow-outbound
    cidr_blocks = ["0.0.0.0/0"]
  }
  tags = { Name = "tf-web-sg" }
}
[CODE lang=hcl caption="compute.tf - launch template and ASG"]
resource "aws_launch_template" "web" {
  name_prefix   = "tf-web-"
  image_id      = var.ami_id
  instance_type = "t3.micro"
  key_name      = var.key_name
  vpc_security_group_ids = [aws_security_group.web.id]   # no subnet here - the ASG decides that, not the template
  user_data = base64encode(<<-EOF
    #!/bin/bash
    dnf install -y nginx
    systemctl enable --now nginx
  EOF
  )
}

resource "aws_autoscaling_group" "web" {
  name                = "tf-web-asg"
  min_size            = 2
  desired_capacity    = 2
  max_size            = 4
  vpc_zone_identifier = aws_subnet.private[*].id        # [*] = both private subnets - app tier, matching the VPC page
  health_check_type   = "ELB"                            # reacts to the target group's health check, not just EC2 status
  health_check_grace_period = 300
  target_group_arns  = [aws_lb_target_group.web.arn]     # registers/deregisters instances automatically

  launch_template {
    id      = aws_launch_template.web.id
    version = "$Latest"
  }

  tag {
    key                 = "Name"
    value               = "tf-web-asg-instance"
    propagate_at_launch = true
  }
}
[CODE lang=hcl caption="loadbalancer.tf - target group, ALB, listener"]
resource "aws_lb_target_group" "web" {
  name     = "tf-web-tg"
  port     = 80
  protocol = "HTTP"
  vpc_id   = aws_vpc.main.id                             # vpc_id only - no subnet_ids argument exists on this resource

  health_check {
    path                = "/"
    healthy_threshold   = 2
    unhealthy_threshold = 2
    interval            = 15
  }
}

resource "aws_lb" "web" {
  name               = "tf-web-alb"
  internal           = false                             # false = internet-facing, must sit in public subnets
  load_balancer_type = "application"
  subnets            = aws_subnet.public[*].id
  security_groups    = [aws_security_group.web.id]
}

resource "aws_lb_listener" "web" {
  load_balancer_arn = aws_lb.web.arn
  port              = 80
  protocol          = "HTTP"
  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.web.arn
  }
}
[CODE lang=hcl caption="outputs.tf"]
output "alb_dns_name" {
  value = aws_lb.web.dns_name                            # the one thing you actually need after apply
}

output "vpc_id" {
  value = aws_vpc.main.id
}
[CODE lang=bash caption="run it"]
terraform init                                            # downloads the AWS provider plugin, sets up the backend
terraform plan -out=tfplan                                 # review every resource it intends to create - read it
terraform apply tfplan                                     # executes exactly what plan showed, nothing more
terraform output alb_dns_name                               # once apply finishes
curl http://$(terraform output -raw alb_dns_name)           # should return nginx's default page, same as every page so far

[STAGE troubleshoot]
HEADING: Changing one line, and what terraform plan actually warns you about
[P]
A reasonable-looking change: you decide `us-east-1a`/`us-east-1b` should be swapped on the two public subnets, to match a naming convention someone on the team prefers. You edit `var.azs`'s default straight in `variables.tf` and run `terraform plan` before applying, like you should.
[CODE lang=bash caption="the plan output - read every line before you ever consider applying"]
terraform plan

  # aws_subnet.public[0] must be replaced
-/+ resource "aws_subnet" "public" {
      ~ availability_zone = "us-east-1a" -> "us-east-1b" # forces replacement
      ~ id                = "subnet-0abc..." -> (known after apply)
        ...
    }
  # aws_route_table_association.public[0] must be replaced
-/+ resource "aws_route_table_association" "public" {
      ~ subnet_id = "subnet-0abc..." -> (known after apply) # forces replacement
    }

Plan: 2 to add, 0 to change, 2 to destroy.

[P]
Two resources marked for destruction, not just an update — and this is on your fresh parallel stack where it's harmless. The exact same one-line change on infrastructure actually serving traffic would destroy and recreate a real subnet, briefly taking down everything inside it.

[STAGE key-insight]
HEADING: "-/+" means destroy and recreate, not update in place
[NOTE]
A subnet's Availability Zone is immutable at the AWS API level, not a Terraform limitation — this is the exact same constraint from the VPC page's doubt about why a subnet's AZ can't be edited after creation. Terraform doesn't invent this restriction; it just honestly surfaces it in the plan output as "forces replacement" instead of quietly trying an in-place update that the API would reject. `~` alone means a safe in-place update. `-/+` means destroy-then-create — and Terraform will cheerfully execute that if you approve the plan, with zero extra warning beyond what's already sitting right there in the output. Reading plan output line by line, specifically checking for `-/+` on anything you didn't expect to be destructive, is the single habit that prevents this from becoming a real production incident instead of a one-line diff.
